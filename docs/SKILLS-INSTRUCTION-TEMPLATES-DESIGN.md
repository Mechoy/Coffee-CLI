# Coffee CLI Skills 与启动指令模板复盘

> 文档状态：Reviewed / Backlog，暂不进入实现
>
> 文档版本：0.1
>
> 更新日期：2026-08-10
>
> 适用范围：Coffee CLI 桌面端的单 Agent 会话与多 Agent Pane；不包含 Web-Home

---

## 1. 决策摘要

Coffee CLI **暂不建设跨 CLI 的通用 Skills 平台**。

值得保留的方向是一个很轻的“启动指令模板”（Instruction Template，也可在 UI
中称为“工作规范”）能力：它帮助用户在新会话开始时复用简短、稳定的方法说明，
减少每次重复交代背景和约束。

它不应被称为 Coffee 的通用 Skill runtime，原因是 Claude、Codex、OpenCode
及其他 CLI 对 Skill 的发现位置、格式、优先级和恢复语义没有共同合同。Coffee
不应猜测、重写或安装这些原生 Skill。

核心边界如下：

| 能力 | 正确职责 | 不能承担的职责 |
|---|---|---|
| MCP 配置组 | 配置本次会话可连接的工具和服务 | 指挥模型按步骤工作，或强制工具调用 |
| 启动指令模板 | 提供一次性的领域方法、输出习惯和注意事项 | 维护状态、推进阶段、验收结果或限制权限 |
| 多 Agent 协同 | Pane 身份、任务投递和临时协作 | 批量作业状态机或流程验收 |
| Agent Runs | 未来负责阶段、审批、重试、结果契约和恢复 | 替代模型的领域知识 |
| 工具包装/系统策略 | 执行真正的权限和输入输出约束 | 依赖模型记住自然语言规则 |

因此，启动指令模板可以降低重复说明和起步成本，但不能解决“模型长期工作后
忘记限制”的全部问题。需要强制执行的规则仍应放在确定性工具、校验器或未来
Agent Runs 的状态机中。

---

## 2. 复盘：为什么会想到 Skills

重复工作往往存在稳定的开场信息：目标范围、检查顺序、输出格式、不可做事项、
以及推荐的工具组合。每次手工重复这些内容会造成三个问题：

1. 用户启动任务前的描述成本高，且容易漏写某条要求。
2. 多个对象或多个会话使用相同方法时，提示词逐渐产生漂移。
3. 会话变长、压缩、切换对象或 Agent 调用工具后，早期软性约束可能被弱化。

Skill 对前两个问题有价值：它能把方法和示例从临时对话中抽出来，形成用户可见、
可复用的起始材料。

但它无法可靠解决第三个问题。模型看到指令不代表程序能够证明模型遵守了指令；
模型说“完成”也不代表产物、阶段或外部副作用满足条件。现有
`docs/AGENT-RUNS-PRD.md` 已把这一点定义为产品边界：Skill 是软提示，不是
状态机、权限边界或结果契约。

## 3. 当前架构事实

### 3.1 MCP 已解决的部分

现有 MCP 设计是正确的控制边界：Coffee 保存服务、配置组和工作区绑定，解析为
会话计划后由 Claude、Codex 或 OpenCode 自己作为 MCP Client 连接服务。

```text
Coffee MCP 配置
  -> SessionMcpPlan
  -> 各 CLI 的会话级原生配置
  -> Agent CLI 发现工具
  -> 模型自行决定是否调用
```

这条链路不需要 Coffee 向模型重复解释“当前 Profile 叫什么”或列出完整能力清单。
实际 MCP 工具 schema 已由 Agent CLI 提供给模型。模板也无法消除这些 schema 的
上下文成本；真正减少无关工具成本的手段仍然是使用小而专一的 MCP Profile。

### 3.2 原生 Skill 没有统一合同

仓库中已能看到不同工具的不同约定，例如 OpenCode 使用 XDG 下的 skills 目录，
OpenClaw 使用自己的 workspace skills 目录。这些事实不能推出一个可由 Coffee
统一管理的 Skill 格式，更不能假定其他 CLI 的扫描、优先级、热更新或 resume
行为相同。

若 Coffee 现在实现“统一安装、发现、同步、版本管理”，会形成第二套不兼容的
生态，同时与各 CLI 的原生能力、未来插件机制和用户已有配置冲突。

### 3.3 Agent Runs 已覆盖强控制需求

`docs/AGENT-RUNS-PRD.md` 中的 Agent Runs 已被记录为待办。它未来负责对稳定、
重复的工作对象维护阶段、Attempt、审批、结构化结果和恢复状态。

Agent Runs 可以引用一份指令模板的不可变快照或内容 hash，但模板不能替代 Run
的状态机。二者必须保持单向关系：Run 使用模板，不由模板驱动执行。

## 4. 最终产品定位

如果未来满足立项条件，Coffee 应提供的是**用户显式选择的启动指令模板**，而不
是“模型根据语义自动找 Skill”的系统。

建议的用户语义：

```text
新建会话
  -> 用户选择可选的工作规范
  -> Coffee 显示将使用的 MCP Profile 建议和适用 CLI
  -> 用户确认最终 MCP 选择与模板
  -> Coffee 只在本次新会话启动时注入一次简短指令
```

这里的“推荐 MCP Profile”只是启动建议：用户可改为 `Auto`、`None` 或其他
Profile，最终仍由现有 MCP 解析优先级决定。模板不得偷偷启用工具、扩大权限或
根据自然语言自行选择 Profile。

为了避免与原生工具的 `SKILL.md` 语义混淆，Coffee 内部数据模型和文档应使用
`instruction template` 或 `work guide` 作为名称。用户明确选择某个本地
`SKILL.md` 时，可以把它当作普通 Markdown 指令源，而不是宣称已兼容其所属 CLI
的完整 Skill 系统。

## 5. 未来最小范围

### 5.1 模板内容

一个候选模板只允许包含以下无执行能力的数据：

```json
{
  "version": 1,
  "id": "research-summary",
  "name": "Research Summary",
  "supported_agents": ["claude", "codex", "opencode"],
  "instruction_source": {
    "type": "inline",
    "content": "..."
  },
  "recommended_mcp_profile": "research",
  "roles": {
    "default": "Researcher"
  }
}
```

可接受字段：稳定 ID、显示名、适用 CLI、短文本或用户选择的本地 Markdown 来源、
内容 hash/版本、可选推荐 MCP Profile、可选的单 Agent 或 Pane 角色说明。

明确禁止字段：任意 shell 命令、自动安装逻辑、自动 MCP 调用、权限提升、密钥、
环境变量值、定时器、DAG、完成标记或可执行表达式。

### 5.2 会话注入语义

1. 仅在**新建原生会话**时，通过对应 CLI 已验证的会话级适配器注入一次。
2. Coffee 不在每一轮对话重新提醒，不进行后台提示或定时重注入。
3. 原生 `resume`、历史恢复和多 Agent 工作区恢复不得再次注入，避免篡改已有
   对话上下文或重复消耗 token。
4. 模板修改只影响之后新建的会话；已运行会话保持启动时版本。
5. 无法可靠注入的 CLI 不得显示“已应用”；只能明确降级为用户手工复制，或不
   在选择器中提供该 CLI。

多 Agent 首版不应把一个模板自动扩散到所有 Pane。每个 Pane 都必须显式选择角色
和模板，默认没有模板。恢复工作区只保存模板 ID、来源和内容 hash 用于展示漂移，
不保存全文、密钥或临时路径。

### 5.3 Token 与存储边界

- 模板必须有小的正文上限；详细参考资料应由用户在任务中按需提供，而不是整份
  自动注入。
- Coffee 应显示注入文本大小，并拒绝超限内容，而不是悄悄截断。
- 不因为选择模板而发起模型诊断请求、意图分类请求或 MCP 健康轮询。
- 不持久化完整的运行期注入文本到多 Agent 快照；只保存可验证的 ID、hash 和
  用户可读名称。
- 临时指令文件复用现有会话临时产物生命周期，退出和 Pane 清理时删除，防止
  磁盘无界增长。

## 6. 绝对不做的设计

以下方案会让 Coffee 膨胀、增加 token 或制造错误的可靠性承诺，因此不进入此
方向的任何初版：

- 根据用户自然语言自动匹配模板或自动启用 MCP。
- 每轮对话重新发送 Skill 全文、能力清单或规则摘要。
- 修改 `~/.codex`、`~/.claude`、`~/.config/opencode` 或项目目录来安装 Coffee
  的 Skill。
- 统一 Skill 商店、下载器、自动更新器或跨 CLI 同步服务。
- 自动扫描用户磁盘上所有 Markdown/Skill 文件并隐式信任其中内容。
- 将 Markdown 当作安全边界，或以模型是否遵守文字来判定权限和作业成功。
- 以终端中的 `DONE` 文本、模型自述或自由文本为流程推进依据。
- 对已恢复的原生会话热更新模板或二次注入指令。

## 7. 风险与控制

| 风险 | 后果 | 控制方式 |
|---|---|---|
| 模型仍忽略指令 | 用户误以为约束被强制执行 | 明确标注为建议；硬约束移入工具或 Agent Runs |
| CLI 注入语义不同 | 某些工具没有实际收到模板 | 每个 CLI 单独验证；不支持即显式拒绝 |
| Markdown 含提示注入或密钥 | 指令污染或敏感信息泄露 | 只接受用户显式来源；限制大小；不自动扫描或同步 |
| 模板和 MCP Profile 漂移 | 新会话得到意外能力组合 | 显示最终解析 Profile；记录模板 hash；用户确认 |
| 多 Pane 重复注入 | token 和工具上下文放大 | 默认无继承；每 Pane 显式选择 |
| 临时文件或快照增长 | 磁盘被长期占用 | 复用会话清理机制；快照只保存元数据且设大小上限 |
| 模板被误用于流程控制 | 跳步、重复副作用、错误完成 | 只由未来 Agent Runs 维护阶段、审批和结构化验收 |

---

## 8. 进入实现前的门槛

该方向不因“可以实现”而自动立项。开始实现前必须同时满足：

1. 收集至少 3 次真实、跨领域的重复任务样本，证明稳定的起始说明确实被反复
   使用，且简单保存提示词不足以解决问题。
2. 样本不应只来自某个安全测试场景，避免 Coffee 被错误收窄为行业工具。
3. 对计划支持的 Claude、Codex、OpenCode 分别验证 fresh launch、restart、
   native resume、全局配置共存和失败回退。
4. 证明不会修改全局 CLI 配置或项目文件，也不会因为选择模板发送额外模型请求。
5. 确认文本大小上限、临时文件清理和恢复快照的 hash 漂移显示方式。
6. 证明 MCP Profile 的最终解析结果可在启动前展示，且模板不会静默扩大工具权限。

若其中任一条件不成立，继续使用现有的 MCP Profile、Task Board 和用户手工起始
提示即可，不应为了功能数量而增加一个半可靠的系统。

---

## 9. 建议验证顺序

### Phase 0：不改产品 UI 的兼容性验证

用一个极小、不可持久化的内部原型验证每个 CLI 的单次注入语义：

1. 新会话是否收到一次且仅一次的短指令。
2. 原生 resume 是否不会二次注入。
3. MCP 参数和用户已有原生配置是否保持不变。
4. 注入失败能否可靠地返回给 Coffee，而不是显示假成功。
5. 退出后是否没有残留模板正文或临时文件。

Phase 0 只产出兼容性证据，不创建设置页、模板库或迁移逻辑。

### Phase 1：最小可用模板

只有 Phase 0 和真实使用样本均通过后，才考虑：

- 本地模板的创建、编辑、复制、删除和手动选择；
- 启动前预览：模板名称、内容 hash、注入大小、适用 CLI、最终 MCP Profile；
- 新会话的一次性注入与显式失败状态；
- 多 Agent 的每 Pane 明确角色/模板选择；
- 与工作区恢复的元数据记录和 drift 提示。

### Phase 2：与 Agent Runs 的受控引用

Agent Runs 获批实施后，可以让一个 Stage 引用用户确认的 Markdown 指令源，并在
Run 启动时冻结内容快照。这个能力遵循 `AGENT-RUNS-PRD.md` 的结果契约和状态机，
不把普通模板升级为调度器。

---

## 10. 结论

Skills 的需求是真实的，但其正确价值是“减少重复的起始说明”，不是“让模型永远
记住并遵守规则”。

当前 Coffee 已有的 MCP 配置组应继续专注能力管理；未来 Agent Runs 应继续专注
可验证的执行状态。两者之间保留一个小而明确的启动指令模板层即可。没有真实
样本和 CLI 兼容性证据之前，不应开始开发 UI 或跨 CLI Skill 平台。
